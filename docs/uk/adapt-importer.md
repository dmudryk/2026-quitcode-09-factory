# Як адаптувати імпортер під формат вимог вашого PM

Імпортер `tools/ac-to-task.mjs` перетворює вимогу PM на задачу фабрики. Він навмисно малий (~180 рядків) і має шість
позначених місць для змін — «ТОЧКА РОЗШИРЕННЯ 1…6». Код фабрики не змінюється: ви змінюєте лише імпортер (і, якщо зміниться
вигляд ID, — `scripts/factory-tap.mjs` у двійнику).

## Що імпортер має видати

Задачу, у якій **ID критерію PM = ID вимоги у фабриці = назва рядка TAP**. Лише так ланцюжок «AC → тест → зміна → доказ»
не рветься: PM бачить у proof pack ті самі `AC-…`, що й у своїй вимозі.

```json
{
  "id": "x-db",
  "title": "…",
  "requirements": [
    { "id": "AC-X-01", "description": "Дано … Коли … Тоді …", "verifiedBy": ["visible:AC-X-01", "holdout:x-db"] }
  ],
  "nonFunctionals": { "security": "TBD", "accessRules": "TBD", "idempotency": "TBD", "tenancy": "TBD", "failureModes": "TBD" },
  "visibleTests": { "failToPass": ["AC-X-01"], "passToPass": ["AC-OLD-01", "…"] },
  "holdouts": ["x-db"],
  "protected": ["tests/**", "scripts/**", "…"]
}
```

`TBD` — свідомо: нефункціональні вимоги вирішує людина. `F approve intent` таку задачу ще прийме, але `F run` відмовить на
допуску (`task not admissible`, `non-functional "…" is still undecided`, $0). Заповнили — затвердьте intent знову.

## Чотири поширені формати

Перші три імпортер читає «з коробки» (перевірено тестами `tests/ws9.test.mjs`). Четвертий — приклад власної адаптації.

### 1. Файл вимоги, критерій — один рядок (типово, `--format lines`)

Так виглядає шаблон вимоги з WS6–WS8: `docs/requirements/*.md` у репо PM, синхронізований у `requirements/` розробника.

```markdown
# Вимога: масове рішення менеджера
## Навіщо
Менеджер погоджує заявки по одній…
## Критерії приймання
- AC-BULK-01: Дано … Коли … Тоді …
1. AC-BULK-02 Дано … Коли … Тоді …
### AC-BULK-03: Дано … Коли … Тоді …
```

```powershell
node tools\ac-to-task.mjs --file C:\pf\twin\requirements\02-bulk.md --ac AC-BULK-01,AC-BULK-02 --id bulk-db `
  --holdout bulk-db --target C:\pf\twin --size small --out C:\pf\control\tasks\bulk-db.json
```

### 2. GitHub issue з чекбоксами (`--issue`)

PM веде вимоги в issues, критерії — чекбоксами, ID жирним:

```markdown
- [ ] **AC-BULK-01** — Дано … Коли … Тоді …
- [x] **AC-BULK-02** — Дано … Коли … Тоді …
```

```powershell
node tools\ac-to-task.mjs --issue <власник>/<репо-pm>#14 --ac AC-BULK-01,AC-BULK-02 --id bulk-db --target C:\pf\twin --out …
```

Тіло issue читається через `gh issue view` (потрібен вхід у `gh` з доступом до репо PM). Назва задачі — заголовок issue.

### 3. Таблиця критеріїв (`--format table`)

```markdown
| ID | Дано | Коли | Тоді |
|---|---|---|---|
| AC-REP-01 | є три заявки за місяць | менеджер натискає «Експорт» | завантажується CSV з трьома рядками |
```

Перша клітинка — ID, решта склеюється в опис: «є три заявки за місяць · менеджер натискає «Експорт» · …».

### 4. Багаторядковий блок «Дано / Коли / Тоді» (`--format block`)

```markdown
### AC-REM-01 — нагадування за день
- **Дано** заявка починається завтра
- **Коли** настає 9:00
- **Тоді** людина отримує лист-нагадування
```

Блок триває до наступного заголовка. Якщо ваш PM пише інакше — наприклад Gherkin (`Scenario:` / `Given` / `When` / `Then`) чи
критерії в Jira-експорті, — додайте свою функцію в `PARSERS` (ТОЧКА РОЗШИРЕННЯ 3) за зразком `block`.

## Інші точки розширення

| Точка | Що змінювати | Коли |
|---|---|---|
| 1. `AC_ID` | регулярний вираз ID | PM пише `AC-3.2`, `US12-AC1` тощо. **Той самий вираз** змініть у `scripts/factory-tap.mjs` (`AC` і `AC_IN_SOURCE`), інакше фабрика не знайде рядок TAP |
| 2. `readSource` | звідки береться текст | Jira, Linear, Notion: експортуйте в markdown або додайте читання через їх CLI; поверніть `{ text, source }` |
| 4. `parseTitleAndWhy` | назва задачі і «навіщо» | заголовок вимоги чи розділ «Навіщо» називаються інакше |
| 5. `implementedAcs` | що вже реалізовано (pass-to-pass) | статус реалізації не в `docs/conformance.md` або колонка називається інакше |
| 6. `PROTECTED` | що будівельнику не можна змінювати | інша структура тестів, інша назва конфігурації Vitest |

## Перевірка адаптації

1. Запустіть імпорт на справжній вимозі PM і порівняйте `requirements[].description` з текстом вимоги — дослівно.
2. `--target` має дати попередження лише для критеріїв без Vitest-тесту (лише e2e або ще не написані).
3. Додайте фрагмент формату PM у `tests/fixtures/ws9/` і тест у `tests/ws9.test.mjs` за зразком наявних — `npm test`.
4. Закомітьте зміну імпортера з коротким описом: який формат, що змінено, як перевірено (для бонусу — 5 рядків у звіті).

щоб для кожного критерію ID збігався з ID у вимозі, а опис — дослівно з тексту «Дано / Коли / Тоді». Не змінюй
